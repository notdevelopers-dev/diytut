# Бекенд

Python + FastAPI + SQLAlchemy (async) + Alembic. Як підняти весь стек локально — у [головному README](../README.md#швидкий-старт).

Усі інструменти (uv, Alembic, ruff, pytest) запускаються всередині контейнера `api`, а не на машині розробника.

## Організація коду

- **Ендпоінти** згруповані за темами: кожна група — окремий роутер. Усі роутери підключаються в одному місці під спільним префіксом `/api`, тож сам префікс записаний лише раз.
- **Налаштування** читаються зі змінних оточення в одному модулі конфігурації. Якщо обов'язкової змінної немає, застосунок не стартує й одразу каже, чого бракує.
- **Сесія БД** видається кожному запиту через залежність FastAPI і закривається автоматично.
- **Моделі** успадковуються від спільного базового класу. Кожну нову модель треба зареєструвати в пакеті моделей.
- **Імена індексів і обмежень** генеруються автоматично за спільною конвенцією; задавати їх вручну не потрібно.

## Вхід через Google

Вхід працює за схемою OAuth 2.0 Authorization Code (з PKCE) поверх OpenID Connect. Увесь обмін із Google відбувається на бекенді, а фронтенд лише веде користувача на `/api/auth/google/login`.

- Після повернення з Google бекенд перевіряє ID-токен і шукає користувача за `sub` з Google, а не за email.
- Відомий користувач отримує JWT сесії в HttpOnly-cookie `session` на 7 днів.
- Для нового користувача в БД нічого не пишеться: дані з Google зберігаються в короткоживучій cookie `registration`, і його перенаправлено на форму реєстрації. Запис з'являється лише після відправлення форми.
- `POST /api/auth/register` перевіряє поля форми, створює користувача й одразу видає сесію. Нікнейм зберігається в нижньому регістрі, а якщо його не вказали — генерується. Телефон приводиться до вигляду `+380XXXXXXXXX`, вік має бути від 18 років. Помилки полів мають той самий формат, що й помилки валідації FastAPI: 422 для неправильних даних, 409 для зайнятого нікнейма.
- `GET /api/auth/me` повідомляє фронтенду, чи користувач увійшов, чи має завершити реєстрацію; `POST /api/auth/logout` видаляє cookie.
- Для користувача, що увійшов, `GET /api/auth/me` також повертає його організацію (`id`, `name`, `status` і його `role`) або `null`. З цього фронтенд знає, чи показувати перемикач між режимом волонтера й режимом організації.
- Ендпоінти, що вимагають входу, отримують id користувача через залежність `CurrentUserId`.

Ключі OAuth-клієнта створюються в Google Cloud Console, а дозволені redirect URI там мають збігатися з `GOOGLE_REDIRECT_URI`. Локально `COOKIE_SECURE` вимкнено, бо там немає HTTPS.

Тести працюють зі справжньою БД, тож перед ними потрібно застосувати міграції. Кожен тест виконується в транзакції, яку потім відкочують, тож дані в БД тести не змінюють.

## Організації

- `POST /api/organizations` створює організацію від імені користувача, що увійшов, і в тій самій транзакції записує його в `organization_members` з роллю `owner`.
- Нова організація має статус `pending`, доки її не перегляне адміністратор.
- Поки що користувач може належати лише до однієї організації: це обмеження є і в БД. Повторна спроба дає 409, зайнятий код ЄДРПОУ — 409 з помилкою поля `edrpou`, як і для нікнейма.
- `GET /api/organizations/me` повертає профіль організації користувача разом з його роллю в ній; доступно будь-якому учаснику. Якщо користувач не належить до організації — 404.
- `PATCH /api/organizations/me` змінює лише передані поля: `email`, `phone`, `city_id`, `description`. Назву й код ЄДРПОУ перевіряє адміністратор, тому їх змінити не можна (422). Явний `null` очищує опис, а для обов'язкових полів дає 422.
- Змінювати профіль можуть лише `owner` і `admin`, і лише поки організацію не заблоковано; інакше 403. Рядки членства й організації блокуються до збереження змін, тож роль і статус не можуть змінитися між перевіркою й записом.
- Режим організації на сайті — стан фронтенду, а не сесії: права перевіряються за членством і роллю в БД, тож окремого входу в організацію чи виходу з неї на бекенді немає. Вихід з акаунта — `POST /api/auth/logout`.

## Профіль волонтера

- `GET /api/users/me` повертає профіль авторизованого волонтера разом із даними про його місто.
- `PATCH /api/users/me` частково оновлює профіль користувача (`first_name`, `last_name`, `patronymic`, `nickname`, `phone`, `birth_date`, `gender`, `city_id`, `bio`). Поля блокуються на час транзакції для захисту від перегонів. Зайнятий іншим користувачем нікнейм повертає 409, неіснуюче місто — 422.
- `GET /api/users/me/organizations` повертає список організацій, до яких належить користувач, для перемикання акаунтів / режимів на фронтенді.

## Залежності

- Залежності керуються через uv: додавати й видаляти пакети лише його командами, lock-файл руками не редагувати. Ним можна керувати у контейнері api.
- Опис залежностей і lock-файл комітяться разом.
- Інструменти лише для розробки (лінтер, тести) додаються в окрему dev-групу й не потрапляють у продакшн-образ.
- Версія Python зафіксована в базовому образі; опис проєкту й локальні налаштування uv тримають ту саму мінорну гілку.

## Схема бази даних

Схемою керує лише Alembic.

- Міграцію генерують з різниці між моделями й поточною БД, а потім обов'язково переглядають вручну. Автогенерація — чернетка, а не готовий результат.
- **Перейменування Alembic не розпізнає:** він подасть його як «видалити + створити», і дані зникнуть. Такі місця виправляються вручну на явне перейменування.
- Міграції, які вже потрапили в `main`, не змінюються; потрібна зміна — нова міграція.
- Одна міграція на PR, і перед злиттям — свіжий `main`. Якщо двоє паралельно створили міграції, після злиття їх треба об'єднати окремою merge-міграцією.
- Перед застосуванням можна переглянути SQL, який виконає міграція, нічого не змінюючи в БД.

## Лінт і форматування

```bash
docker compose exec api uv run ruff check .          # знайти проблеми
docker compose exec api uv run ruff check --fix .    # виправити те, що можна автоматично
docker compose exec api uv run ruff format .         # відформатувати код
```

Перед комітом коду бажано проходити `ruff check .` і `ruff format --check .` без помилок.
