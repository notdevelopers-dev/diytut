# Бекенд

Python + FastAPI + SQLAlchemy (async) + Alembic. Як підняти весь стек локально — у [головному README](../README.md#швидкий-старт).

Усі інструменти (uv, Alembic, ruff, pytest) запускаються всередині контейнера `api`, а не на машині розробника.

## Організація коду

- **Ендпоінти** згруповані за темами: кожна група — окремий роутер. Усі роутери підключаються в одному місці під спільним префіксом `/api`, тож сам префікс записаний лише раз.
- **Налаштування** читаються зі змінних оточення в одному модулі конфігурації. Якщо обов'язкової змінної немає, застосунок не стартує й одразу каже, чого бракує.
- **Сесія БД** видається кожному запиту через залежність FastAPI і закривається автоматично.
- **Моделі** успадковуються від спільного базового класу. Кожну нову модель треба зареєструвати в пакеті моделей.
- **Імена індексів і обмежень** генеруються автоматично за спільною конвенцією; задавати їх вручну не потрібно.

## Вхід через Google

Вхід працює за схемою OAuth 2.0 Authorization Code (з PKCE) поверх OpenID Connect. Увесь обмін із Google відбувається на бекенді, а фронтенд лише веде користувача на `/api/auth/google/login`.

- Після повернення з Google бекенд перевіряє ID-токен і шукає користувача за `sub` з Google, а не за email.
- Відомий користувач отримує JWT сесії в HttpOnly-cookie `session` на 7 днів.
- Для нового користувача в БД нічого не пишеться: дані з Google зберігаються в короткоживучій cookie `registration`, і його перенаправлено на форму реєстрації. Запис з'являється лише після відправлення форми.
- `POST /api/auth/register` перевіряє поля форми, створює користувача й одразу видає сесію. Нікнейм зберігається в нижньому регістрі, а якщо його не вказали — генерується. Телефон приводиться до вигляду `+380XXXXXXXXX`, вік має бути від 18 років. Помилки полів мають той самий формат, що й помилки валідації FastAPI: 422 для неправильних даних, 409 для зайнятого нікнейма.
- `GET /api/auth/me` повідомляє фронтенду, чи користувач увійшов, чи має завершити реєстрацію; `POST /api/auth/logout` видаляє cookie.
- Для користувача, що увійшов, `GET /api/auth/me` також повертає його організацію (`id`, `name`, `status` і його `role`) або `null`. З цього фронтенд знає, чи показувати перемикач між режимом волонтера й режимом організації. Якщо організацій кілька, це організація за замовчуванням (див. [Організації](#організації)).
- Ендпоінти, що вимагають входу, отримують id користувача через залежність `CurrentUserId`.

Ключі OAuth-клієнта створюються в Google Cloud Console, а дозволені redirect URI там мають збігатися з `GOOGLE_REDIRECT_URI`. Локально `COOKIE_SECURE` вимкнено, бо там немає HTTPS.

### Dev-вхід без Google

Щоб локально не потрібні були ключі OAuth-клієнта, у доповненні для розробки ввімкнено `DEV_LOGIN`. Тоді `GOOGLE_*` можна лишити порожніми, а `/api/auth/google/login` веде не на Google, а на сторінку `/api/auth/dev/login`:

- новий email веде на форму реєстрації фронтенду так само, як після Google (ім'я й прізвище можна передзаповнити);
- email наявного користувача одразу дає сесію, тож можна входити й в акаунти, створені через справжній Google; список останніх користувачів є на сторінці.

Перевірити справжній вхід через Google локально — `DEV_LOGIN=false` і ключі в `.env`. В основному описі стеку змінна не передається, а з `COOKIE_SECURE=true` застосунок із `DEV_LOGIN` не стартує, тож на сервері dev-вхід увімкнути не вийде. Без `DEV_LOGIN` порожні `GOOGLE_*` зупиняють застосунок на старті.

Тести працюють зі справжньою БД, тож перед ними мають бути застосовані міграції (у стеку це робить `migrate`). Кожен тест виконується в транзакції, яку потім відкочують, тож дані в БД тести не змінюють.

## Організації

- `POST /api/organizations` створює організацію від імені користувача, що увійшов, і в тій самій транзакції записує його в `organization_members` з роллю `owner`.
- Нова організація має статус `pending`, доки її не перегляне адміністратор.
- Користувач може створити кілька організацій і належати до кількох. Зайнятий код ЄДРПОУ дає 409 з помилкою поля `edrpou`, як і для нікнейма.
- Організація за замовчуванням — та, до якої користувач приєднався найраніше. З нею працюють запити, що не називають організацію, тож клієнт, який не знає про кілька організацій, завжди бачить і змінює одну й ту саму.
- Іншу організацію обирає параметр `?organization_id=` у `GET` і `PATCH /api/organizations/me` та в `GET /api/organizations/me/projects`, а також поле `organization_id` у тілі `POST /api/projects`. Організація, до якої користувач не належить, дає 404 для профілю і 403 для створення проєкту. Роль і статус перевіряються саме в обраній організації.
- `GET /api/organizations/me` повертає профіль організації користувача разом з його роллю в ній; доступно будь-якому учаснику. Якщо користувач не належить до жодної організації — 404.
- `PATCH /api/organizations/me` змінює лише передані поля: `email`, `phone`, `city_id`, `description`. Назву й код ЄДРПОУ перевіряє адміністратор, тому їх змінити не можна (422). Явний `null` очищує опис, а для обов'язкових полів дає 422.
- Змінювати профіль можуть лише `owner` і `admin`, і лише поки організацію не заблоковано; інакше 403. Рядки членства й організації блокуються до збереження змін, тож роль і статус не можуть змінитися між перевіркою й записом.
- Режим організації на сайті — стан фронтенду, а не сесії: права перевіряються за членством і роллю в БД, тож окремого входу в організацію чи виходу з неї на бекенді немає. Вихід з акаунта — `POST /api/auth/logout`.

## Заявки на вступ до організації

- `POST /api/organizations/{id}/join-requests` з тілом `{"message": "..."}` (необов'язково, до 1000 символів) подає заявку на вступ від імені користувача, що увійшов; 201 і заявка в статусі `pending`.
  - Несхвалена організація (`pending`, `rejected`, `blocked`) для волонтера не існує: 404, як і для неіснуючої.
  - Друга заявка до тієї ж організації, поки перша на розгляді, — 409. Обмеження є й у БД (частковий унікальний індекс), тож паралельні запити теж дають 409. Після рішення можна подати нову.
  - Учасник цієї організації подати заявку не може (409). Членство в інших організаціях не заважає.
  - Власник організації отримує сповіщення `join_request_received` (`link` — `/organization/join-requests?organization_id={id}`) у тій самій транзакції, що й заявка.
- `GET /api/organizations/{id}/my-request-status` — остання заявка поточного користувача до організації з будь-яким статусом; 404, якщо заявок не було.
- `GET /api/organizations/me/join-requests?organization_id=&limit=20&offset=0` — заявки на розгляді до організації користувача, давніші першими, разом з іменем, нікнеймом і містом волонтера (без контактів). Як і в інших `/me`, без `organization_id` — організація за замовчуванням. Лише для `owner` і `admin` обраної організації, іншим учасникам 403; без організації чи для організації, до якої користувач не належить, — 404.
- `PATCH /api/join-requests/{id}` з тілом `{"status": "accepted" | "rejected"}` розглядає заявку; відповідь — заявка з `reviewed_by` і `reviewed_at`.
  - Прийняття в одній транзакції змінює статус заявки, додає волонтера в `organization_members` з роллю `member` і створює йому сповіщення `join_request_accepted`; відхилення — статус і сповіщення `join_request_rejected` (`link` в обох — `/organizations/{id}`).
  - Розглядати можуть лише `owner` і `admin` організації, до якої подано заявку, і лише поки її не заблоковано (403). Роль перевіряється саме в цій організації, хоч би якою була організація рецензента за замовчуванням. Заявки чужої організації відповідають 404, як неіснуючі.
  - Розглянути можна лише заявку в статусі `pending`, інакше 409; рядок заявки блокується, тож два рішення по одній заявці не пройдуть одночасно.
  - Членство волонтера в інших організаціях не заважає. Якщо ж за час розгляду він уже став учасником цієї організації, прийняти заявку не можна (409), а відхилити можна.
  - Цим самим ендпоінтом розглядаються й заявки на проєкти, з власними перевірками: див. [Заявки на участь у проєктах](#заявки-на-участь-у-проєктах).

### Відомі обмеження

- **Повторні заявки на вступ після відхилення нічим не обмежені.** (Для заявок на проєкти є пауза й ігнор, див. нижче.) Волонтер може одразу подати нову заявку до організації, що його відхилила, і так скільки завгодно разів; кожна дає власнику сповіщення. Можливі рішення: пауза після відхилення (наприклад, 7 днів, за `reviewed_at` останньої заявки, без міграції) або ліміт відхилених заявок до однієї організації. У MVP свідомо не зроблено.

## Проєкти

- `POST /api/projects` створює проєкт від імені організації користувача: поле `organization_id`, а без нього — організація за замовчуванням. Створювати можуть лише `owner` і `admin`, і лише поки організацію не заблоковано; іншим учасникам, користувачам поза організацією й заблокованій організації — 403.
  - `"status": "published"` (за замовчуванням) — проєкт одразу публікується з повною перевіркою полів (див. нижче). Лише для схваленої організації, інакше 403.
  - `"status": "draft"` — чернетка (R-12, рішення 18.11). Обов'язкова лише назва `title`, решту можна заповнити пізніше. Передані поля перевіряються одразу: кількість місць (до 2 147 483 647) і години (до 999.99) більші за 0, кінець після початку, до двох сфер зі сталого набору, до п'яти хештегів, місто існує. Повноту полів перевіряє публікація. Чернетку може зберегти й організація, що чекає на схвалення чи отримала відмову: поза організацією її ніхто не бачить.
  - Інші статуси при створенні — 422: завершує й скасовує проєкт сервер.
- **Повна перевірка** однакова для створення опублікованого проєкту й для публікації чернетки. Обов'язкові `description`, `starts_at`, `ends_at`, `capacity`, `volunteer_hours` і від однієї до двох сфер, кінець має бути після початку, а офлайн-подія потребує `city_id` і `address`. Помилки — 422 у форматі помилок полів FastAPI (`loc: ["body", "<поле>"]`), і для публікації збереженої чернетки теж, хоч тіла запиту там немає: так форма проєкту показує їх біля полів однаково. Усі помилки приходять одним списком: некоректні значення, відсутні поля й зв'язки між полями (порядок дат і місце офлайн-події, `loc: ["body"]`), тож виправити все можна за одну спробу.
- `POST /api/projects/{id}/publish` публікує чернетку; відповідь — проєкт зі статусом `published` і часом публікації `published_at`.
  - Лише `owner` і `admin` організації проєкту (іншим учасникам 403), лише поки організація схвалена й не заблокована (403). Для користувача поза організацією чернетки не існує: 404.
  - Опублікувати можна лише чернетку, інакше 409. Бракує полів — 422 з переліком, і чернетка лишається чернеткою.
  - Рядки членства, організації й проєкту блокуються до збереження: роль, статус організації й статус проєкту не зміняться між перевіркою й записом, а дві публікації не пройдуть одночасно.
- Обмеження продубльовані в БД. Для будь-якого статусу, крім `draft`, обов'язкові ці поля та `published_at` (`ck_projects_complete_unless_draft`), місце офлайн-події (`ck_projects_offline_has_location`) і хоча б одна сфера (`ck_projects_categories_count`). Заповнені поля чернетки й там мають бути коректними.
- **Видимість.** `GET /api/projects/{id}` без входу й для сторонніх віддає лише опубліковані проєкти. Учасники організації проєкту з будь-якою роллю бачать і її чернетки, завершені й скасовані проєкти; для решти такого проєкту не існує (404). Недійсна сесія тут не дає 401, а вважається гостем.
- `GET /api/projects` (каталог) показує лише опубліковані проєкти, що ще не завершилися. Нові йдуть першими за часом публікації `published_at`, тож чернетка, опублікована пізніше, теж потрапляє нагору. Профіль організації `GET /api/organizations/{id}` теж показує лише опубліковані.
- `GET /api/organizations/me/projects?organization_id=&status=&limit=20&offset=0` — усі проєкти організації для кабінету: чернетки, опубліковані, завершені й скасовані; `status` звужує список до одного статусу. Нові першими за часом створення, у відповіді `items` і `total` для пагінації. Доступно будь-якому учаснику обраної організації; без організації чи для чужої — 404.

### Відомі обмеження

- Права перевіряються за фіксованими ролями `owner` і `admin`. З кастомними ролями (задача 508) створення й публікація мають вимагати права «створювати й редагувати проєкти».
- Змінити чернетку поки не можна: редагування — задача 503.
- Дата початку не перевіряється на майбутнє ні при створенні, ні при публікації. Чернетку, дата якої минула, можна опублікувати, але в каталозі її не буде, якщо подія вже завершилася.

## Заявки на участь у проєктах

Волонтер подає заявку на конкретний проєкт без членства в організації (R-23), а організація її розглядає з урахуванням кількості місць (R-24). Заявки зберігаються в тій самій `join_requests` з `target = 'project'` і `project_id`.

Статуси: `pending` → `accepted` або `rejected` (рішення організації), а також `cancelled`, коли волонтер сам відкликав заявку. Фронтенд показує їх як «Запит очікує», «Ви учасник», «Запит відхилено», а для `cancelled` знову «Приєднатись».

- `POST /api/projects/{id}/join-requests` з тілом `{"message": "..."}` (необов'язково, до 1000 символів) подає заявку; 201 і заявка в статусі `pending`.
  - Чернетка, скасований проєкт і проєкт несхваленої організації для волонтера не існують: 404. Проєкт, що вже почався, — 409.
  - Власник і адміни організації не подають заявок на її проєкти (409). Звичайний учасник організації може.
  - Вимоги проєкту: `is_adult_only` — 18 років на день початку події за київським часом, `experience_level` — рівень волонтера не нижчий (інакше 403). Рівень обчислюється із суми підтверджених годин, див. [Участь, години й відгуки](#участь-години-й-відгуки).
  - Якщо схвалених заявок уже стільки, скільки місць (`capacity`), — 409. Це попередня перевірка: остаточно місця рахуються під час розгляду.
  - Одна активна заявка (`pending` чи `accepted`) на проєкт, інакше 409. Обмеження є й у БД (частковий унікальний індекс `uq_join_requests_active_user_project`), тож паралельні запити теж дають 409. Після скасування можна подати нову одразу.
  - **Пауза після відмови.** Повторна заявка на той самий проєкт можлива лише через 10 с після останньої відмови, і з кожною наступною відмовою на цей проєкт пауза вп'ятеро довша: 50 с, ~4 хв, ~21 хв, ~1,7 год, ~8,7 год, ~1,8 доби, а з восьмої — тиждень (верхня межа). Раніше — 429 із заголовком `Retry-After` (секунди до кінця паузи). Відмови на інших проєктах не враховуються. Константи — `REAPPLY_*` в `app/services/project_join_requests.py`.
  - Волонтер з ігнору організації (див. нижче) подати заявку на жоден її проєкт не може: 403.
  - Власник і адміни організації отримують сповіщення `join_request_received` у тій самій транзакції, що й заявка.
- `GET /api/projects/{id}/my-request-status` — остання заявка поточного користувача на проєкт з будь-яким статусом; 404, якщо заявок не було. Поле `can_reapply_at` — лише для відхиленої заявки: коли закінчиться пауза й можна подати нову. `null`, якщо повторна заявка неможлива: волонтер в ігнорі (так ігнор виглядає звичайною відмовою) або проєкт уже почався.
- `GET /api/projects/my-request-statuses?project_id=1&project_id=2` — те саме для кількох проєктів одним запитом (до 100 id), щоб картки каталогу не робили запит кожна: nginx обмежує 10 запитів на секунду з IP. Проєктів без заявок у відповіді немає.
- `DELETE /api/projects/{id}/my-request` — скасувати свою заявку (`pending` чи вже `accepted`) до початку події; відповідь — заявка зі статусом `cancelled`. Схвалена заявка так звільняє місце. Немає активної заявки — 404, подія вже почалася — 409. Власник і адміни отримують `join_request_cancelled`.
- `GET /api/users/me/project-requests?limit=20&offset=0` — усі заявки поточного користувача на проєкти, свіжіші першими, з коротким описом проєкту (`project`).
- `GET /api/projects/{id}/join-requests?status=pending&limit=20&offset=0` — заявки на проєкт для організації: давніші першими, разом з іменем, нікнеймом і містом волонтера, сумою його підтверджених годин (`confirmed_hours`) і рівнем (`experience_level`, R-27). `status=accepted` дає склад учасників. Лише для `owner` і `admin` організації проєкту, іншим учасникам 403; чужий проєкт — 404.
- `PATCH /api/join-requests/{id}` (той самий, що для заявок на вступ) з тілом `{"status": "accepted" | "rejected", "ignore": false}`:
  - Прийняти можна, лише поки проєкт опублікований і не почався, і лише якщо є вільне місце (409). Рядок проєкту блокується на час рішення, тож паралельні прийняття не перевищать `capacity`. Відхилити можна будь-коли.
  - Членом організації волонтер від прийняття не стає.
  - Скасовану волонтером заявку розглянути не можна (409).
  - Волонтер отримує `join_request_accepted` чи `join_request_rejected` з назвою проєкту.
- **Ігнор.** `"ignore": true` разом із `"status": "rejected"` додає волонтера в ігнор організації (`organization_ignored_users`): він більше не може подавати заявки на жоден її проєкт. Волонтер отримує звичайне сповіщення про відмову, без згадки про ігнор. `ignore` разом із прийняттям чи для заявки на вступ до організації — 422. Повторний ігнор нічого не змінює.
  - `GET /api/organizations/me/ignored-users?organization_id=&limit=20&offset=0` — список ігнору, свіжіші першими: волонтер, хто й коли додав.
  - `DELETE /api/organizations/me/ignored-users/{user_id}?organization_id=` — зняти ігнор; 204, а якщо волонтера в ігнорі немає — 404.
  - Обидва лише для `owner` і `admin`, як і розгляд заявок.

### Відомі обмеження

- Після ігнору інші заявки волонтера на проєкти цієї організації лишаються на розгляді: їх треба відхилити окремо.
- Місце й час події ще бачать усі, а не лише підтверджені учасники (R-22).

## Профіль волонтера

- `GET /api/users/me` повертає профіль авторизованого волонтера разом із даними про його місто.
- `PATCH /api/users/me` частково оновлює профіль користувача (`first_name`, `last_name`, `patronymic`, `nickname`, `phone`, `birth_date`, `gender`, `city_id`, `bio`). Поля блокуються на час транзакції для захисту від перегонів. Зайнятий іншим користувачем нікнейм повертає 409, неіснуюче місто — 422.
- `GET /api/users/me/organizations` повертає список організацій, до яких належить користувач, для перемикання акаунтів / режимів на фронтенді. Список іде від найдавнішої, тож перша в ньому — організація за замовчуванням.

## Адмін-панель

Усі ендпоінти під `/api/admin` доступні лише користувачам з `platform_role = admin`: без входу — 401, звичайному користувачу — 403. Роль перевіряється в БД на кожен запит, тож зняті права діють одразу, без чекання на закінчення сесії. Адміністратора призначають напряму в БД.

### Заявки на створення організацій

- `GET /api/admin/organizations?status=pending&search=&limit=20&offset=0` — список заявок разом із містом і контактами того, хто подав заявку, та `total` для пагінації. Найстаріші йдуть першими; без `status` повертаються організації з будь-яким статусом.
  - `search` (до 200 символів) шукає частину назви без урахування регістру або частину ЄДРПОУ; `%` і `_` у запиті — звичайні символи. Пошук працює разом зі `status`, а `total` рахує заявки з урахуванням обох.
- `GET /api/admin/organizations/{id}` — одна заявка.
- `POST /api/admin/organizations/{id}/review` з тілом `{"decision": "approved" | "rejected", "comment": "..."}` розглядає заявку: змінює статус і записує, хто, коли й з яким коментарем її розглянув. Коментар обов'язковий при відхиленні. Розглянути можна лише заявку в статусі `pending`, інакше 409; рядок організації блокується, тож два адміністратори не розглянуть її одночасно.

### Статистика входів

> **⚠️ Записуються лише УСПІШНІ входи.** Невдалі спроби (Google відмовив, email не підтверджено, сесія OAuth зламалася тощо) не потрапляють у БД ніяк, і поля «статус» у `login_events` немає. Тому статистика й список останніх входів не показують ні помилок входу, ні спроб підбору. Якщо колись знадобиться облік невдалих спроб, потрібні нове поле або окрема таблиця і міграція, а фронтенд має перестати вважати кожен запис успішним.

- Кожен успішний вхід записується в `login_events`: через Google, одразу після реєстрації чи через dev-вхід (`method`). Початок реєстрації новим користувачем входом не вважається. Записи лишаються й після видалення акаунта, лише без `user_id`.
- Разом із входом записується IP клієнта (`ip`, тип `inet`). Це адреса, яку бачить API: у продакшні nginx бере її з `CF-Connecting-IP`, а uvicorn — з `X-Forwarded-For` (`--proxy-headers`). Якщо адреса не є IP (так буває в тестах), записується `NULL`; у входах до появи цього поля IP теж порожній.
- `GET /api/admin/stats/logins/recent?limit=20&offset=0` — останні входи, свіжіші першими, і `total` для пагінації: час, `method`, `ip` і користувач (`id`, `email`, ім'я, прізвище, `platform_role`). Якщо акаунт видалено, `user` — `null`.
- `GET /api/admin/stats/logins?date_from=2026-03-01&date_to=2026-03-31` повертає кількість входів і унікальних користувачів за період і по кожному дню, зокрема дні без входів. Дні рахуються за київським часом. Без параметрів — останні 30 днів; період не довший за 366 днів, інакше 422.

#### Відомі обмеження

- IP у `login_events` — персональні дані, а записи не видаляються автоматично й лишаються навіть після видалення акаунта. Строку зберігання й очищення поки немає.
- Роль у списку входів — лише роль на платформі (`user`/`admin`). Чи представляє користувач організацію, звідси не видно: організацій у нього може бути кілька.

## Сповіщення

- Сповіщення в застосунку зберігаються в `notifications`: адресат (`user_id`), `type`, `title`, `message`, `is_read`, необов'язковий `link` (відносний шлях на фронтенді) і `created_at`.
- `type` — enum у БД, тож новий тип сповіщення потребує міграції. Типи покривають рішення, зміни статусів і нарахування, які волонтер має бачити в сповіщеннях:
  - власнику організації — нова заявка на вступ (`join_request_received`); власнику й адмінам — нова заявка на проєкт і її скасування волонтером (`join_request_received`, `join_request_cancelled`);
  - волонтеру — рішення щодо заявки на вступ чи на проєкт, скасування проєкту, нарахування годин (зокрема 0) і новий рівень досвіду (`join_request_accepted`, `join_request_rejected`, `project_cancelled`, `hours_credited`, `level_up`);
  - обом сторонам — можливість залишити відгук після нарахування годин (`review_available`);
  - творцю організації — рішення адміністратора платформи; причина відхилення пишеться в `message` (`organization_approved`, `organization_rejected`).
- Композитний індекс `(user_id, is_read)` обслуговує лічильник непрочитаних і список сповіщень користувача; окремого індексу на `user_id` немає, бо його покриває цей.
- Типи `join_request_*` спільні для заявок на вступ до організації й на проєкт: що саме, видно з тексту й посилання. Якщо фронтенду треба розрізняти їх за типом, потрібні окремі значення enum і міграція.
- Сповіщення видаляються разом з користувачем.
- Сповіщення створює `create_notification` з `app/notifications.py`. Вона лише додає запис у сесію, а зберігає його `commit` того, хто викликав: сповіщення з'являється разом із подією, про яку повідомляє, і зникає разом із нею за відкату.
- Шляхи для `link` будують функції там само. **Їх ще має підтвердити фронтенд**, частини маршрутів там поки немає; змінювати їх лише разом із маршрутами фронтенду.
- Зараз сповіщення надсилаються творцю організації, коли адміністратор платформи її схвалює чи відхиляє, а також про заявки на вступ і на проєкти (див. відповідні розділи).

### Посилання: тимчасове рішення

Зараз бекенд формує готовий шлях на фронтенді й зберігає його в `link`, бо так задумано в моделі. Це найпростіше, але має недоліки: бекенд мусить знати маршрути фронтенду, а після їх зміни вже збережені сповіщення ведуть на старі адреси.

| `type` | `link` |
| --- | --- |
| `organization_approved` | `/organization?organization_id={id}` |
| `organization_rejected` | `/organization/edit?organization_id={id}` |
| `join_request_received` (заявка на вступ) | `/organization/join-requests?organization_id={id}` |
| `join_request_accepted`, `join_request_rejected` (заявка на вступ) | `/organizations/{id}` |
| `join_request_received`, `join_request_cancelled` (заявка на проєкт) | `/organization/projects/{project_id}/join-requests?organization_id={id}` |
| `join_request_accepted`, `join_request_rejected` (заявка на проєкт) | `/projects/{project_id}` |

Сторінки кабінету організації отримують `?organization_id=`, як і `/api/organizations/me`: користувач може належати до кількох організацій, і без id незрозуміло, котрої стосується сповіщення. Фронтенд, який поки не знає про кілька організацій, може цей параметр ігнорувати.

Якщо шляхи не підходять, їх треба узгодити й змінити в `app/notifications.py`. Якщо підхід не підходить загалом, архітектурно чистіше зберігати замість шляху id пов'язаних об'єктів (окремі колонки `organization_id`, `project_id`… або JSONB `payload`), а шлях з `type` та id будуватиме фронтенд. Це потребує міграції, тож варто вирішити до того, як сповіщень із посиланнями стане багато.

### API сповіщень

Усі ендпоінти вимагають входу й працюють лише зі сповіщеннями поточного користувача: чуже сповіщення відповідає 404, як неіснуюче.

- `GET /api/notifications?limit=50&offset=0` — сповіщення, нові першими; не більше 50 за запит.
- `GET /api/notifications/unread-count` — `{"count": n}` для лічильника в шапці.
- `PATCH /api/notifications/{id}/read` — позначити прочитаним; повторний виклик не є помилкою.
- `POST /api/notifications/read-all` — позначити прочитаними всі; відповідь `{"updated": n}`.

## Участь, години й відгуки

- `attendances` — підтверджена організатором участь волонтера в проєкті: `project_id`, `user_id`, нараховані `hours`, хто й коли підтвердив (`confirmed_by`, `confirmed_at`). Запис з'являється лише під час підтвердження після події; до того участь описує схвалена заявка в `join_requests`.
- `hours` можуть бути дробовими й відрізнятися від планових годин проєкту. `0` означає, що волонтер не прийшов: запис усе одно створюється, щоб рішення не ухвалили вдруге.
- Пара `(project_id, user_id)` унікальна: це захист від подвійного нарахування годин на рівні БД. Виправлення годин — зміна наявного запису, а не новий запис.
- Пізніші виправлення годин видно з `updated_at`; `confirmed_at` лишається часом першого підтвердження.
- Окремого стовпця з балансом годин у `users` немає: баланс — це сума `hours` у записах участі волонтера.
- Рівень досвіду теж не зберігається, а обчислюється з балансу функцією `level_for_hours` з `app/models/experience.py` за таблицею R-27: до 50 годин включно — `novice`, до 150 — `interested`, до 300 — `amateur`, до 500 — `experienced`, далі — `pro`.
- `feedbacks` — відгук після підтвердженої участі: `rating` від 1 до 5 і необов'язковий `comment`. Відгук прив'язаний до запису участі (`attendance_id`), тож проєкт і волонтер відомі з неї, а без запису участі відгук не створити. Запис із `hours = 0` БД теж приймає: відгуки лише після ненульового нарахування (R-28) має перевіряти сервіс.
- `target` показує, про кого відгук: `project` — волонтер про проєкт, `volunteer` — організація про волонтера; `author_id` — хто його написав. Кожна сторона залишає один відгук за одну участь: пара `(attendance_id, target)` унікальна.
- `target` — enum у БД, тож нове значення потребує міграції.
- Видалення акаунта знеособлює ці записи, а не видаляє їх: `user_id`, `confirmed_by` і `author_id` стають `NULL`, а години й оцінки лишаються в статистиці проєкту й платформи. Текст відгуку організації про видаленого волонтера БД сама не прибирає.

## Залежності

- Залежності керуються через uv: додавати й видаляти пакети лише його командами, lock-файл руками не редагувати. Ним можна керувати у контейнері api.
- Опис залежностей і lock-файл комітяться разом.
- Інструменти лише для розробки (лінтер, тести) додаються в окрему dev-групу й не потрапляють у продакшн-образ.
- Версія Python зафіксована в базовому образі; опис проєкту й локальні налаштування uv тримають ту саму мінорну гілку.

## Схема бази даних

Схемою керує лише Alembic.

- Міграції застосовує сервіс `migrate` при кожному `docker compose up`, а `api` чекає на його успішне завершення. Локально код змонтовано в контейнер, тож щойно створену міграцію застосує `docker compose up -d` або `docker compose run --rm migrate`.

- Міграцію генерують з різниці між моделями й поточною БД, а потім обов'язково переглядають вручну. Автогенерація — чернетка, а не готовий результат.
- **Перейменування Alembic не розпізнає:** він подасть його як «видалити + створити», і дані зникнуть. Такі місця виправляються вручну на явне перейменування.
- Міграції, які вже потрапили в `main`, не змінюються; потрібна зміна — нова міграція.
- Одна міграція на PR, і перед злиттям — свіжий `main`. Якщо двоє паралельно створили міграції, після злиття їх треба об'єднати окремою merge-міграцією.
- Перед застосуванням можна переглянути SQL, який виконає міграція, нічого не змінюючи в БД.

## Лінт і форматування

```bash
docker compose exec api uv run ruff check .          # знайти проблеми
docker compose exec api uv run ruff check --fix .    # виправити те, що можна автоматично
docker compose exec api uv run ruff format .         # відформатувати код
```

Перед комітом коду бажано проходити `ruff check .` і `ruff format --check .` без помилок.
