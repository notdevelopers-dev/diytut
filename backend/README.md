# Бекенд

Python + FastAPI + SQLAlchemy (async) + Alembic. Як підняти весь стек локально — у [головному README](../README.md#швидкий-старт).

Усі інструменти (uv, Alembic, ruff, pytest) запускаються всередині контейнера `api`, а не на машині розробника.

## Організація коду

- **Ендпоінти** згруповані за темами: кожна група — окремий роутер. Усі роутери підключаються в одному місці під спільним префіксом `/api`, тож сам префікс записаний лише раз.
- **Налаштування** читаються зі змінних оточення в одному модулі конфігурації. Якщо обов'язкової змінної немає, застосунок не стартує й одразу каже, чого бракує.
- **Сесія БД** видається кожному запиту через залежність FastAPI і закривається автоматично.
- **Моделі** успадковуються від спільного базового класу. Кожну нову модель треба зареєструвати в пакеті моделей.
- **Імена індексів і обмежень** генеруються автоматично за спільною конвенцією; задавати їх вручну не потрібно.

## Вхід через Google

Вхід працює за схемою OAuth 2.0 Authorization Code (з PKCE) поверх OpenID Connect. Увесь обмін із Google відбувається на бекенді, а фронтенд лише веде користувача на `/api/auth/google/login`.

- Після повернення з Google бекенд перевіряє ID-токен і шукає користувача за `sub` з Google, а не за email.
- Відомий користувач отримує JWT сесії в HttpOnly-cookie `session` на 7 днів.
- Для нового користувача в БД нічого не пишеться: дані з Google зберігаються в короткоживучій cookie `registration`, і його перенаправлено на форму реєстрації. Запис з'являється лише після відправлення форми.
- `POST /api/auth/register` перевіряє поля форми, створює користувача й одразу видає сесію. Нікнейм зберігається в нижньому регістрі, а якщо його не вказали — генерується. Телефон приводиться до вигляду `+380XXXXXXXXX`, вік має бути від 18 років. Помилки полів мають той самий формат, що й помилки валідації FastAPI: 422 для неправильних даних, 409 для зайнятого нікнейма.
- `GET /api/auth/me` повідомляє фронтенду, чи користувач увійшов, чи має завершити реєстрацію; `POST /api/auth/logout` видаляє cookie.
- Для користувача, що увійшов, `GET /api/auth/me` також повертає його організацію (`id`, `name`, `status` і його `role`) або `null`. З цього фронтенд знає, чи показувати перемикач між режимом волонтера й режимом організації. Якщо організацій кілька, це організація за замовчуванням (див. [Організації](#організації)).
- Ендпоінти, що вимагають входу, отримують id користувача через залежність `CurrentUserId`.

Ключі OAuth-клієнта створюються в Google Cloud Console, а дозволені redirect URI там мають збігатися з `GOOGLE_REDIRECT_URI`. Локально `COOKIE_SECURE` вимкнено, бо там немає HTTPS.

### Dev-вхід без Google

Щоб локально не потрібні були ключі OAuth-клієнта, у доповненні для розробки ввімкнено `DEV_LOGIN`. Тоді `GOOGLE_*` можна лишити порожніми, а `/api/auth/google/login` веде не на Google, а на сторінку `/api/auth/dev/login`:

- новий email веде на форму реєстрації фронтенду так само, як після Google (ім'я й прізвище можна передзаповнити);
- email наявного користувача одразу дає сесію, тож можна входити й в акаунти, створені через справжній Google; список останніх користувачів є на сторінці.

Перевірити справжній вхід через Google локально — `DEV_LOGIN=false` і ключі в `.env`. В основному описі стеку змінна не передається, а з `COOKIE_SECURE=true` застосунок із `DEV_LOGIN` не стартує, тож на сервері dev-вхід увімкнути не вийде. Без `DEV_LOGIN` порожні `GOOGLE_*` зупиняють застосунок на старті.

Тести працюють зі справжньою БД, тож перед ними мають бути застосовані міграції (у стеку це робить `migrate`). Кожен тест виконується в транзакції, яку потім відкочують, тож дані в БД тести не змінюють.

## Організації

- `POST /api/organizations` створює організацію від імені користувача, що увійшов, і в тій самій транзакції записує його в `organization_members` з роллю `owner`.
- Нова організація має статус `pending`, доки її не перегляне адміністратор.
- Користувач може створити кілька організацій і належати до кількох. Зайнятий код ЄДРПОУ дає 409 з помилкою поля `edrpou`, як і для нікнейма.
- Організація за замовчуванням — та, до якої користувач приєднався найраніше. З нею працюють запити, що не називають організацію, тож клієнт, який не знає про кілька організацій, завжди бачить і змінює одну й ту саму.
- Іншу організацію обирає параметр `?organization_id=` у `GET` і `PATCH /api/organizations/me` та поле `organization_id` у тілі `POST /api/projects`. Організація, до якої користувач не належить, дає 404 для профілю і 403 для створення проєкту. Роль і статус перевіряються саме в обраній організації.
- `GET /api/organizations/me` повертає профіль організації користувача разом з його роллю в ній; доступно будь-якому учаснику. Якщо користувач не належить до жодної організації — 404.
- `PATCH /api/organizations/me` змінює лише передані поля: `email`, `phone`, `city_id`, `description`. Назву й код ЄДРПОУ перевіряє адміністратор, тому їх змінити не можна (422). Явний `null` очищує опис, а для обов'язкових полів дає 422.
- Змінювати профіль можуть лише `owner` і `admin`, і лише поки організацію не заблоковано; інакше 403. Рядки членства й організації блокуються до збереження змін, тож роль і статус не можуть змінитися між перевіркою й записом.
- Режим організації на сайті — стан фронтенду, а не сесії: права перевіряються за членством і роллю в БД, тож окремого входу в організацію чи виходу з неї на бекенді немає. Вихід з акаунта — `POST /api/auth/logout`.

## Профіль волонтера

- `GET /api/users/me` повертає профіль авторизованого волонтера разом із даними про його місто.
- `PATCH /api/users/me` частково оновлює профіль користувача (`first_name`, `last_name`, `patronymic`, `nickname`, `phone`, `birth_date`, `gender`, `city_id`, `bio`). Поля блокуються на час транзакції для захисту від перегонів. Зайнятий іншим користувачем нікнейм повертає 409, неіснуюче місто — 422.
- `GET /api/users/me/organizations` повертає список організацій, до яких належить користувач, для перемикання акаунтів / режимів на фронтенді. Список іде від найдавнішої, тож перша в ньому — організація за замовчуванням.

## Адмін-панель

Усі ендпоінти під `/api/admin` доступні лише користувачам з `platform_role = admin`: без входу — 401, звичайному користувачу — 403. Роль перевіряється в БД на кожен запит, тож зняті права діють одразу, без чекання на закінчення сесії. Адміністратора призначають напряму в БД.

### Заявки на створення організацій

- `GET /api/admin/organizations?status=pending&limit=20&offset=0` — список заявок разом із містом і контактами того, хто подав заявку, та `total` для пагінації. Найстаріші йдуть першими; без `status` повертаються організації з будь-яким статусом.
- `GET /api/admin/organizations/{id}` — одна заявка.
- `POST /api/admin/organizations/{id}/review` з тілом `{"decision": "approved" | "rejected", "comment": "..."}` розглядає заявку: змінює статус і записує, хто, коли й з яким коментарем її розглянув. Коментар обов'язковий при відхиленні. Розглянути можна лише заявку в статусі `pending`, інакше 409; рядок організації блокується, тож два адміністратори не розглянуть її одночасно.

### Статистика входів

- Кожен успішний вхід записується в `login_events`: через Google, одразу після реєстрації чи через dev-вхід (`method`). Початок реєстрації новим користувачем входом не вважається. Записи лишаються й після видалення акаунта, лише без `user_id`.
- `GET /api/admin/stats/logins?date_from=2026-03-01&date_to=2026-03-31` повертає кількість входів і унікальних користувачів за період і по кожному дню, зокрема дні без входів. Дні рахуються за київським часом. Без параметрів — останні 30 днів; період не довший за 366 днів, інакше 422.

## Сповіщення

- Сповіщення в застосунку зберігаються в `notifications`: адресат (`user_id`), `type`, `title`, `message`, `is_read`, необов'язковий `link` (відносний шлях на фронтенді) і `created_at`.
- `type` — enum у БД, тож новий тип сповіщення потребує міграції. Типи покривають рішення, зміни статусів і нарахування, які волонтер має бачити в сповіщеннях:
  - власнику організації — нова заявка на проєкт і скасування заявки волонтером (`join_request_received`, `join_request_cancelled`);
  - волонтеру — рішення щодо заявки, скасування проєкту, нарахування годин (зокрема 0) і новий рівень досвіду (`join_request_accepted`, `join_request_rejected`, `project_cancelled`, `hours_credited`, `level_up`);
  - обом сторонам — можливість залишити відгук після нарахування годин (`review_available`);
  - творцю організації — рішення адміністратора платформи; причина відхилення пишеться в `message` (`organization_approved`, `organization_rejected`).
- Композитний індекс `(user_id, is_read)` обслуговує лічильник непрочитаних і список сповіщень користувача; окремого індексу на `user_id` немає, бо його покриває цей.
- Сповіщення видаляються разом з користувачем.

## Участь, години й відгуки

- `attendances` — підтверджена організатором участь волонтера в проєкті: `project_id`, `user_id`, нараховані `hours`, хто й коли підтвердив (`confirmed_by`, `confirmed_at`). Запис з'являється лише під час підтвердження після події; до того участь описує схвалена заявка в `join_requests`.
- `hours` можуть бути дробовими й відрізнятися від планових годин проєкту. `0` означає, що волонтер не прийшов: запис усе одно створюється, щоб рішення не ухвалили вдруге.
- Пара `(project_id, user_id)` унікальна: це захист від подвійного нарахування годин на рівні БД. Виправлення годин — зміна наявного запису, а не новий запис.
- Пізніші виправлення годин видно з `updated_at`; `confirmed_at` лишається часом першого підтвердження.
- Окремого стовпця з балансом годин у `users` немає: баланс — це сума `hours` у записах участі волонтера.
- `feedbacks` — відгук після підтвердженої участі: `rating` від 1 до 5 і необов'язковий `comment`. Відгук прив'язаний до запису участі (`attendance_id`), тож проєкт і волонтер відомі з неї, а без запису участі відгук не створити. Запис із `hours = 0` БД теж приймає: відгуки лише після ненульового нарахування (R-28) має перевіряти сервіс.
- `target` показує, про кого відгук: `project` — волонтер про проєкт, `volunteer` — організація про волонтера; `author_id` — хто його написав. Кожна сторона залишає один відгук за одну участь: пара `(attendance_id, target)` унікальна.
- `target` — enum у БД, тож нове значення потребує міграції.
- Видалення акаунта знеособлює ці записи, а не видаляє їх: `user_id`, `confirmed_by` і `author_id` стають `NULL`, а години й оцінки лишаються в статистиці проєкту й платформи. Текст відгуку організації про видаленого волонтера БД сама не прибирає.

## Залежності

- Залежності керуються через uv: додавати й видаляти пакети лише його командами, lock-файл руками не редагувати. Ним можна керувати у контейнері api.
- Опис залежностей і lock-файл комітяться разом.
- Інструменти лише для розробки (лінтер, тести) додаються в окрему dev-групу й не потрапляють у продакшн-образ.
- Версія Python зафіксована в базовому образі; опис проєкту й локальні налаштування uv тримають ту саму мінорну гілку.

## Схема бази даних

Схемою керує лише Alembic.

- Міграції застосовує сервіс `migrate` при кожному `docker compose up`, а `api` чекає на його успішне завершення. Локально код змонтовано в контейнер, тож щойно створену міграцію застосує `docker compose up -d` або `docker compose run --rm migrate`.

- Міграцію генерують з різниці між моделями й поточною БД, а потім обов'язково переглядають вручну. Автогенерація — чернетка, а не готовий результат.
- **Перейменування Alembic не розпізнає:** він подасть його як «видалити + створити», і дані зникнуть. Такі місця виправляються вручну на явне перейменування.
- Міграції, які вже потрапили в `main`, не змінюються; потрібна зміна — нова міграція.
- Одна міграція на PR, і перед злиттям — свіжий `main`. Якщо двоє паралельно створили міграції, після злиття їх треба об'єднати окремою merge-міграцією.
- Перед застосуванням можна переглянути SQL, який виконає міграція, нічого не змінюючи в БД.

## Лінт і форматування

```bash
docker compose exec api uv run ruff check .          # знайти проблеми
docker compose exec api uv run ruff check --fix .    # виправити те, що можна автоматично
docker compose exec api uv run ruff format .         # відформатувати код
```

Перед комітом коду бажано проходити `ruff check .` і `ruff format --check .` без помилок.
